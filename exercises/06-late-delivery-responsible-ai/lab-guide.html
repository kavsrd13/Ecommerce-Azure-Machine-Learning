Step 01 / Learning objective

Investigate errors, not just accuracy

At checkout, can we identify orders likely to arrive after the promised calendar date? We train a class-balanced logistic regression model. A model that predicts every order is on time can appear accurate because late orders are uncommon; it would miss the very cases we care about.

The Responsible AI dashboard should help answer: Which late orders are missed? How many on-time orders are falsely flagged? Do errors differ across customer/seller states or journey distances? Which available-at-checkout features influence a prediction?

What this does not proveState is a geographic error cohort, not a protected attribute or proof of discrimination. Explanations describe model behavior, not causal effects. The dataset is historical, and canceled or undelivered orders are excluded, so this is not a production-ready customer notification system.

Plan for 2-3 hours of active instruction plus training time. Use an existing Azure ML workspace with permission to register assets and submit jobs; cluster creation requires additional permissions and quota. Cloud compute and storage incur charges.

Step 05 / Data and target

Prepare four time-split datasets

The script keeps orders marked delivered with an actual date. It summarizes their items to one row per order, joins customer/seller ZIP-prefix coordinates, and engineers distance_km, basket size, order price and weight, purchase month, and promised_days. For a multi-seller order, it uses the seller of the highest-priced item as an approximate route. The target is late_delivery = 1 only when the actual calendar date is after the estimated delivery date. A package arriving later on its promised date is not late.

Training uses purchases before 1 June 2018; test uses June-August 2018. Missing distances are filled using the training median. Smaller stratified copies are used only for the dashboard so explanations finish in reasonable time.

Bash: no Azure charges in this step
"$PY" prepare.py
for split in train test rai-train rai-test; do
  test -f "data/$split/data.parquet" && echo "$split ready"
done

Step 10 / Cloud training

Train the classifier on Azure ML

The command job runs src/train.py on cloud compute. It one-hot encodes the two state columns, scales six numeric features, and fits class-balanced logistic regression. MLflow logs ROC-AUC, average precision, late-class precision/recall, and confusion counts on the full future-period test set. The environment is pinned to the RAI components' responsibleai-tabular:28 runtime so the dashboard can load the saved model.

Bash: opt-in billable training job; keep the returned ID
TRAIN_JOB=$(az ml job create -f jobs/train.yml -g "$RG" -w "$WS" --subscription "$SUB" --query name -o tsv)
printf '%s\n' "$TRAIN_JOB"
az ml job show -n "$TRAIN_JOB" -g "$RG" -w "$WS" --subscription "$SUB" --query status -o tsv

Do not rerun the creation command to check progress. In a new shell set TRAIN_JOB='YOUR-JOB-ID' using your recorded job name and rerun only job show.

Open Azure ML Studio and inspect Jobs > olist-late-delivery-rai. Wait until the job says Completed, then rerun the read-only status command above. The CLI's live job stream command may produce an Incorrect padding error even when the job succeeds; rely on Studio or job show.

Evaluation objectiveA rare-event classifier needs more than accuracy. Higher late recall can come with more false alerts. Decide whether false notifications or missed delays matter more before deploying anything.

Step 12 / Responsible AI pipeline

Generate error analysis and explanations

jobs/rai-dashboard.yml wires four official components: construct the dashboard, run error analysis, compute explanations, then gather them. It uses stratified 2,500-row training and 3,000-row test samples for insight generation, not the full-size evaluation set. The pinned rai_tabular_* components are version 0.22.0; check your region's Azure ML registry if a version is unavailable.

Bash: opt-in billable four-step pipeline; keep the returned ID
RAI_JOB=$(az ml job create -f jobs/rai-dashboard.yml -g "$RG" -w "$WS" --subscription "$SUB" --query name -o tsv)
printf '%s\n' "$RAI_JOB"
az ml job show -n "$RAI_JOB" -g "$RG" -w "$WS" --subscription "$SUB" --query status -o tsv
az ml job list -p "$RAI_JOB" -g "$RG" -w "$WS" --subscription "$SUB" --query '[].{step:display_name,status:status}' -o table

For later status checks, reuse RAI_JOB='YOUR-JOB-ID'; never rerun job create just to reconnect. The four rai_tabular_* components remain pinned to 0.22.0.

Wait for all four steps to reach Completed. In Studio, go to Models > olist-late-delivery-rai > Version 1 > Responsible AI and select Olist late-delivery error analysis. A compute instance may be needed for some interactive what-if features, but the precomputed dashboard does not require you to start one.

Do not add causal or counterfactual components blindlyChanging a promised date changes the definition of lateness; changing a customer's state is not a practical intervention. This exercise uses explanations and observed-error cohorts, not claims that a feature caused a delivery delay.
Step 13 / Student interpretation

Explain what the dashboard reveals

First check Model overview for late-class recall, precision, and confusion counts. Then compare error cohorts by customer_state and distance_km. Inspect cohort sample sizes before concluding anything about a small state. Finally, use Explanations to identify the inputs the model relies on, especially promised_days, which is closely linked to the target definition and must really be known when the prediction is made.

QuestionEvidence to record
Does it catch late orders?Late recall, false negatives, and the underlying number of late orders.
Would it bother on-time customers?Late precision and false positives at the current threshold.
Where do errors change?State/distance cohort rates and sample sizes; avoid causal conclusions.
Can we trust the explanation?Confirm features were known at checkout; note the promised date's policy effect.

In the instructor's reference run the future-period late rate was 3.6%; the model caught 521 of 672 late orders but incorrectly flagged 7,860 on-time orders. Your values should be close with the same files and environment. That is a reason to withhold automatic customer alerts and improve the decision rule, not to claim success from recall alone.

Submit your findingsRecord the training and RAI job IDs, registered model version, late precision/recall and confusion counts, one adequately sized cohort observation, one explanation, and a recommendation on whether to deploy or revise.
