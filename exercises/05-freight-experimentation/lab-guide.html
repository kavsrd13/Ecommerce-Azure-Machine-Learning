Step 01 / What are we solving?

Predict shipping cost before quoting it

One row is one order item. The target is its recorded freight_value. We use information available at checkout: product price, weight and dimensions, product category, seller/customer state, approximate distance, basket size and purchase month. Delivery dates and reviews are excluded because they occur later.

The Microsoft Learn exercise uses diabetes classification. Here the equivalent tasks are AutoML regression and manual regression experiments tracked by MLflow. Work only in this cloned exercise; do not run upstream infrastructure scripts.

Step 03 / Feature engineering and split

Build the freight experiment table

The script joins orders, items, products, customers, sellers, category translations and geolocation. It first reduces geolocation to one coordinate pair per ZIP prefix, avoiding duplicated items. It creates distance and volume, then groups all items from the same order in the same chronological split.

Bash: no cloud charges
../../.venv/bin/python prepare.py --raw-data '../../datasets/olist/Ecommerce Dataset'
for split in train validation test; do test -f "data/$split/orders.csv" && echo "$split ready"; done

Step 04 / Versioned Azure ML data

Register the three MLTable assets

Each folder contains orders.csv and an MLTable definition. In the notebook, check all version 1 assets before setting UPLOAD_DATA = True to upload missing ones to your configured workspace. Reuse an existing asset version; never silently replace it with changed data.

In Studio: Data → Data assets. Open each asset and point out its version, type and source folder.
Step 05 / Automated model search

Run bounded AutoML regression

Azure ML compares up to five regression trials using the training asset and the separate April-May validation asset. The job has a 90-minute overall limit and runs only one trial at a time. Its search objective is normalized_root_mean_squared_error; explain that the business will also care about errors in reais.

In the notebook, set SUBMIT_JOBS = True only after reviewing costs and confirming all three version 1 input assets exist. A newly submitted job name is recorded in ignored .freight-run-ids.json; you may also populate it with names of your own existing jobs. Reruns reconnect rather than submitting duplicates.

In Studio: Jobs → olist-freight-automl → the run → Data guardrails and Models + child jobs. Ask students why five trials are not five copies of the same model.
Step 06 / Controlled comparisons

Train Ridge and boosting with MLflow

AutoML searches automatically. Here src/train.py explicitly compares a training-median baseline with one algorithm per Azure ML command job. MLflow logs parameters, validation MAE/RMSE, the percentage within R$5, and a prediction plot. The model file is attached to each Azure job.

The same guarded notebook toggle submits Ridge and boosting as separate jobs. The saved ridge and boosting job IDs belong to your configured workspace, not an instructor's subscription.

In Studio: Jobs → olist-freight-mlflow. Open the two runs and compare baseline_mae_brl with validation_mae_brl. Show the plot under job outputs/MLflow artifacts.
Step 07 / Explain the outcome

Choose using validation data only

The completed Azure ML runs found median-baseline MAE R$8.81, Ridge R$5.63, and boosting R$5.31 on April-May validation rows. Boosting won the manual comparison on MAE. Ask students why the baseline still matters and why the test period was not consulted for this choice.

Use notebook step 9 to inspect the statuses of your recorded jobs without resubmitting them. Compare metrics only on the same validation period.

Teaching questionAutoML minimizes normalized RMSE; the manual jobs report MAE in R$. Can we declare a winner from those two different metrics alone? No: compare candidates on the same metric and validation period.
Step 08 / One final look at future orders

The notebook checks that the selected job completed, registers its MLflow model once and pins its version for the held-out test job; saved IDs prevent duplicate evaluation on reruns.

Step 09 / Discussion and housekeeping

What did the experiment establish?

  • Nine raw Olist CSVs became three time-based, versioned MLTable assets.
  • AutoML compared regression algorithms; manual runs logged reproducible metrics and model artifacts to MLflow.
  • The test period measures future generalization only after model selection. It is not a fresh tuning set.
  • Checkout predictions still need operational validation; the ZIP-prefix distance is not a road journey.
Shared workspaceDo not delete this resource group or someone else's compute. Serverless training stops billing for its VM when the job ends; stored assets remain in the workspace. Check your jobs and compute in Azure ML Studio.

If a job remains queued, inspect its run in Studio for quota or environment issues. If an asset's version already exists, use the registered version or publish a new version. For local MLflow 3.x testing, use SQLite tracking rather than the deprecated file-store backend.
